How does database encryption actually work? +
PER-ORGANIZATION ENVELOPE ENCRYPTION

Protect the data.
Protect the key separately.

Each organization receives a random 256-bit data encryption key (DEK). Warden encrypts selected sensitive fields in the application before writing them to PostgreSQL, using AES-256-GCM with a fresh random nonce for each encryption.

The database stores a versioned v2: value containing the nonce, ciphertext and authentication tag—not the original field value. Authenticated context ties new ciphertext to the organization and field purpose, so it cannot be moved to a different organization or purpose and still decrypt successfully.

What is protected?

Protected endpoint identity and inventory fields, alert content, job payloads and output, BitLocker recovery passwords and selected integration secrets.

Where is the data key?

The database stores an encrypted copy of the DEK. In managed mode, the separate server-held key encryption key (KEK) unwraps it; the raw DEK is cached in application memory.

What changes with BYOK?

A passphrase-derived key wraps the DEK instead. The passphrase and derived key are not persisted. Locking the vault or restarting the process requires unlocking it again; protected reads and writes cannot proceed while locked.

What does this not mean?

This is field-level encryption, not encryption of every database column or a zero-knowledge service. Some operational metadata remains readable. The authorized server can see plaintext when rendering data or dispatching jobs.

HOME: THE CONNECTION AND THE BOUNDARY

The server coordinates.
Your node keeps the files.

Home separates the control plane from file storage. Explore either connection path, then see what is actually saved in each place.

{{ icon('endpoint') }}Employee endpointNormal Warden Agent
Direct mTLS streamICE/STUN finds a peer path
{{ icon('storage') }}Your Home NodeYour Windows / Linux host

Peers first try a direct connection using ICE/STUN. The established peer channel carries an inner mTLS connection: both sides authenticate certificates before file operations.

01Authorize the operation

Warden checks the assignment and issues an Ed25519-signed grant, normally valid for 15 minutes. It is scoped to the organization, device, node, space, folder prefix and permissions.

02Authenticate both peers

The node verifies the certificate identity against the signed grant. P2P mode tries direct traversal; when that fails, outbound HTTPS carries the same encrypted inner mTLS stream through Warden.

03Store and verify the file

The Home Node encrypts file contents at rest with AES-256-GCM authenticated chunks. Sync compares SHA-256 hashes, transfers changed whole files and reports completed, failed or skipped work.

{{ icon('overview') }}

Saved on the Warden server

  • Node registration, addresses, heartbeat and capacity
  • Spaces, quotas, access assignments and node membership
  • Access events, job results and short-lived connection offers / answers
  • Node credential hashes—not the raw bootstrap credential

Job reports can include file paths, counts and errors. Protected job payloads and results use organization field encryption. Home control metadata is not all encrypted.

{{ icon('storage') }}

Saved on your Home Node

  • Encrypted file contents on the configured storage disk
  • Local folder names and file metadata such as sizes, timestamps and hashes
  • The local storage key and TLS private-key material in node configuration
  • Replicas on other nodes you explicitly configure

At-rest encryption protects file contents, not every filename or metadata field. The authorized node decrypts files to serve them; protect the node and its configuration.

{{ icon('compliance') }}

Not retained as cloud file storage

  • No synchronized file contents in the Warden database
  • The HTTPS relay forwards encrypted bytes; it cannot read the inner file stream
  • No Home storage encryption key persisted in the control-plane database

The storage key is generated and handed off during setup, so Warden processes it transiently. Back up the node configuration and key separately: Warden cannot recover a lost storage key. Local endpoint copies remain normal files.

What must the network allow? +

P2P mode needs outbound HTTPS to Warden and tries outbound UDP / STUN for direct connectivity. Windows allows the executable’s direct transport sockets: UDP 55000–55099 on Home Nodes and 55100–55199 on endpoints. Supported routers may supply an automatic mapping; manual port forwarding is not required for the relay fallback.

If UDP traversal fails, both peers can use outbound HTTPS, provided Warden’s relay is reachable. Local-network mode needs a reachable private HTTPS node address; public and hybrid deployments need their configured HTTPS addresses reachable too. Warden Home is a file-transfer path, not a general-purpose VPN for all application traffic.

Removing an access assignment stops new grants. Existing grants can remain valid until expiry, and already-downloaded local copies are not automatically erased.

WINDOWS FIREWALL AND NETWORK CONTROL

Make the rule clear.
Keep management reachable.

Build and deploy Windows Firewall rules from the console, then review what the endpoint reports. These are host firewall controls—not a replacement for your router firewall or an antivirus engine.

  • Allow or block inbound and outbound connections
  • Scope rules to applications, IP addresses, ports and Windows profiles
  • Use saved policies, staged deployments and per-endpoint job results
  • Check reported rules and drift before remediation
A deliberate ownership boundary

Warden enables Windows Firewall on all profiles and replaces only rules prefixed “Warden Managed:”. Existing Windows, domain and third-party rules stay in place.

Warden maintains a separate agent HTTPS allow rule. Its policy validation rejects broad outbound block rules and blocks aimed at the agent executable. Existing external rules or network restrictions can still prevent connectivity.
