# Security policy

## Supported versions

Warden Community is currently alpha software. Security fixes are made on the default branch and included in the next release. Until a stable release exists, older snapshots are not guaranteed to receive backports.

## Reporting a vulnerability

Do not open a public issue for a suspected vulnerability, leaked credential, authentication bypass, tenant-isolation defect, remote-code-execution path, cryptographic weakness, or agent-update weakness.

Use GitHub Private Vulnerability Reporting for this repository. If that channel is unavailable, contact the maintainers through the private security contact published on the repository owner profile. Do not send tenant data, private keys, recovery keys, or customer exports unless a maintainer provides an approved encrypted transfer method.

Include:

- Affected component and version or commit
- Reproduction steps or a minimal proof of concept
- Expected and observed behavior
- Security impact and required privileges
- Whether real tenant or endpoint data may be affected

Maintainers should acknowledge a complete report within three business days, provide a status update within seven business days, and coordinate disclosure after a fix is available. These are targets, not a contractual SLA.

## Scope

Good-faith testing is limited to systems and data you own or are explicitly authorized to test. Do not disrupt hosted services, access another tenant, persist on endpoints, exfiltrate data, or perform denial-of-service testing.

## Release security

Official release artifacts must be generated by the documented release pipeline, accompanied by SHA-256 checksums and an SBOM, and signed when platform signing is available. Source availability does not make an arbitrary binary trusted; agents must continue enforcing server identity, signed commands, update hashes, and tenant authorization.
